## هدف پروژه

این پروژه یک ابزار منفرد نیست؛ پشته‌ای از اجزای مستقل برای دریافت، ذخیره، درخواست و مشاهده وضعیت داده‌های مکانی است. نیاز اصلی این بود که تغییر یا توقف یک جزء، بقیه سیستم را مجبور به بازنویسی نکند.

## معماری

Playwright وظیفه تعامل مرورگر و استخراج را دارد. داده خام ابتدا ذخیره و سپس از طریق سرویس FastAPI برای مراحل بعدی ارائه می‌شود. PostgreSQL منبع وضعیت پایدار است و Alembic تغییر schema را کنترل می‌کند. یک کلاینت دسکتاپ Flet نیز عملیات و وضعیت‌ها را بدون اتصال مستقیم به جزئیات دیتابیس نمایش می‌دهد.

مرز سرویس‌ها با قرارداد مشخص شده است: scraper نتیجه را ثبت می‌کند، requester کار بعدی را claim می‌کند و status service نمای قابل مشاهده می‌دهد. این تفکیک امکان dry-run، retry محدود و تشخیص رکورد تکراری را فراهم می‌کند.

## خطا، امنیت و تست

داده صفحه وب ورودی غیرقابل اعتماد است و پیش از ذخیره نهایی نرمال می‌شود. اطلاعات ورود و تنظیمات مرورگر در محیط اجرا نگهداری می‌شوند. parser و قرارداد API مستقل تست می‌شوند و تست end-to-end فقط برای مسیرهایی استفاده می‌شود که رفتار مرورگر اهمیت دارد.

## وضعیت

پروژه فعال است. نقطه قوت آن استقلال اجزاست؛ هزینه این انتخاب، تنظیمات و مشاهده‌پذیری بیشتر میان سرویس‌هاست. برای ادامه، متریک‌های نرخ موفقیت هر مرحله و سیاست روشن نگهداری snapshotها ضروری است.
