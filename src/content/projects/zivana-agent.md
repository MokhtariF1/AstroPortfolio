## هدف نمونه اولیه

Zivana Agent برای پاسخ‌گویی بر اساس داده اختصاصی هر کسب‌وکار ساخته شد. مسئله اصلی تولید متن روان نبود؛ جلوگیری از ترکیب داده دو کسب‌وکار و اعلام صادقانه نبود پاسخ بود.

## معماری

داده پس از پاک‌سازی به قطعه‌های دارای metadata تبدیل و embedding آن در index جدا یا فیلترشده FAISS ذخیره می‌شود. درخواست FastAPI هویت کسب‌وکار را به retrieval منتقل می‌کند و prompt فقط context بازیابی‌شده را در اختیار مدل قرار می‌دهد. مسیر ingestion از query جداست تا به‌روزرسانی داده قابل پیگیری باشد.

آستانه شباهت و پاسخ «اطلاعات کافی ندارم» بخشی از قرارداد است. LangChain هماهنگی زنجیره و OpenRouter دسترسی مدل را فراهم می‌کنند، اما منطق tenant و مجوز در کد برنامه باقی می‌ماند.

## امنیت، ارزیابی و محدودیت

تست مهم، تلاش برای بازیابی سند tenant دیگر و prompt injection داخل سند است. لاگ نباید متن خصوصی کامل را بی‌دلیل نگهداری کند. پروژه prototype است؛ FAISS برای اثبات مفهوم مناسب است، اما نسخه عملیاتی به ارزیابی پاسخ، سیاست حذف داده، مشاهده‌پذیری و storage متناسب با scale نیاز دارد.

## درس آموخته‌شده

RAG به‌تنهایی تضمین حقیقت نیست. کیفیت قطعه‌بندی، مرز مجوز و امکان امتناع از پاسخ به‌اندازه انتخاب مدل اهمیت دارند.
