ساخت یک چت‌بات که جواب روان تولید کند با ساخت یک دستیار قابل اعتماد که اجازه دارد روی داده واقعی اثر بگذارد، یک مسئله نیست. در پروژه دستیار ثبت کسب‌وکار میخوام، کاربر اطلاعاتی مانند نام، دسته، شهر، شماره تماس و توضیح را در یک گفت‌وگوی فارسی ارائه می‌کرد. خروجی نهایی باید به یک API دیگر ارسال می‌شد و در صورت پذیرش، یک موجودیت واقعی می‌ساخت. همین اثر جانبی ساده، طراحی را از «یک prompt خوب» به مسئله‌ای درباره state، اعتبارسنجی، هم‌زمانی و idempotency تبدیل کرد.

این نوشته شرح راه‌حلی است که برای همان محدودیت‌ها انتخاب کردم. نام endpointها، کلیدها و داده‌های واقعی حذف شده‌اند، اما مسیر تصمیم‌گیری و نمونه کدها از معماری پروژه می‌آیند. هدف ارائه نسخه عمومی یک framework نیست؛ می‌خواهم نشان دهم چرا مدل زبانی را در مرز مشخصی نگه داشتم و بخش قطعی سیستم را به کد معمولی سپردم.

## مسئله واقعی: گفت‌وگو آزاد است، API آزاد نیست

کاربر ممکن است در پیام اول فقط بگوید «یک تعمیرگاه در شیراز دارم». در پیام بعد نام را اضافه کند، بعد شماره تلفن را اصلاح کند و در پایان بخواهد شهر را عوض کند. ترتیب پیام‌ها قابل پیش‌بینی نیست و بعضی عبارت‌ها چند معنی دارند. «مرکز شهر» ممکن است بخشی از آدرس باشد، نه نام شهر. نام دسته‌ای که کاربر می‌گوید نیز الزاماً با شناسه دسته در سامانه مقصد برابر نیست.

در طرف دیگر، API مقصد قرارداد مشخص دارد. برخی فیلدها اجباری‌اند، شناسه شهر باید واقعاً در مقصد وجود داشته باشد، تلفن باید قالب معتبر داشته باشد و رسانه نیز چرخه جداگانه‌ای دارد. یک مدل زبانی می‌تواند از متن برداشت مناسبی داشته باشد، اما تضمین نمی‌کند مقدار پیشنهادی در taxonomy مقصد معتبر است. حتی پاسخ ظاهراً درست مدل ممکن است یک مقدار حدسی باشد.

اگر هر پیام مستقیماً به یک payload ثبت تبدیل شود، چند مشکل به‌وجود می‌آید:

- اصلاح کاربر ممکن است روی داده‌ای اعمال شود که قبلاً ثبت شده است.
- مدل می‌تواند نبود اطلاعات را با حدس پر کند.
- retry پیام یا درخواست HTTP می‌تواند موجودیت تکراری بسازد.
- دو پیام هم‌زمان ممکن است نسخه‌های متفاوت Draft را روی هم بنویسند.
- پاسخ موفق HTTP الزاماً به معنی ساخته‌شدن موجودیت معتبر نیست.

اولین تصمیم من این بود که گفت‌وگو و ثبت نهایی دو مرحله مستقل باشند. گفت‌وگو فقط یک **Draft** را می‌سازد. ثبت اثر جانبی جداگانه است و باید از یک دروازه تأیید عبور کند.

## چرا چند flag جای State Machine را نمی‌گیرد؟

نسخه ابتدایی چنین سیستم‌هایی معمولاً با متغیرهایی مانند `has_name`، `is_complete` و `confirmed` شروع می‌شود. با اضافه‌شدن اصلاح، لغو، خطای مقصد و بازگشت از مرحله تأیید، ترکیب flagها زیاد می‌شود. ممکن است `confirmed=true` باشد اما Draft پس از آن تغییر کرده باشد؛ یا `is_complete=true` بماند در حالی که کاربر شهر را پاک کرده است.

State Machine فضای وضعیت‌های مجاز و انتقال میان آن‌ها را صریح می‌کند. در پروژه من وضعیت‌ها از نظر مفهومی شبیه این‌ها بودند:

```python
from enum import StrEnum

class ConversationState(StrEnum):
    COLLECTING = "collecting"
    NEEDS_RESOLUTION = "needs_resolution"
    READY_FOR_REVIEW = "ready_for_review"
    AWAITING_CONFIRMATION = "awaiting_confirmation"
    SUBMITTING = "submitting"
    COMPLETED = "completed"
    FAILED = "failed"
    CANCELLED = "cancelled"
```

نکته مهم نام وضعیت‌ها نیست. قانون اصلی این است که هر transition پیش‌شرط داشته باشد. Draft ناقص نمی‌تواند مستقیماً وارد `SUBMITTING` شود. تغییر یکی از فیلدهای مؤثر بعد از نمایش خلاصه، تأیید قبلی را باطل می‌کند و سیستم را دوباره به `READY_FOR_REVIEW` برمی‌گرداند. وضعیت `COMPLETED` نیز فقط وقتی ثبت می‌شود که شناسه معتبر مقصد در پاسخ وجود داشته باشد.

این مدل دو مزیت عملی داشت: مسیرهای غیرممکن در کد قابل مشاهده شدند و تست‌ها به‌جای بررسی ترکیب‌های مبهم flag، روی transitionهای مجاز تمرکز کردند.

## Draft ساخت‌یافته، نه تاریخچه چت به‌عنوان منبع حقیقت

تاریخچه پیام برای درک زمینه مفید است، اما منبع حقیقت مناسبی برای عملیات نهایی نیست. اگر برای هر بار ثبت، کل گفت‌وگو دوباره به مدل داده شود و از آن payload بخواهیم، نتیجه می‌تواند با اجرای قبلی فرق کند. همچنین مشخص نیست آخرین اصلاح کاربر دقیقاً کدام مقدار را جایگزین کرده است.

Draft یک مدل Pydantic با فیلدهای صریح است. مقدار، منشأ و وضعیت اعتبار هر بخش جدا نگهداری می‌شود. نمونه ساده‌شده زیر فقط بخشی از قرارداد است:

```python
from pydantic import BaseModel, Field

class ListingDraft(BaseModel):
    title: str | None = Field(default=None, max_length=120)
    description: str | None = Field(default=None, max_length=3000)
    phone: str | None = None
    city_id: int | None = None
    category_id: int | None = None
    address: str | None = None
    revision: int = 0

    @property
    def missing_required(self) -> set[str]:
        required = {
            "title": self.title,
            "city_id": self.city_id,
            "category_id": self.category_id,
            "phone": self.phone,
        }
        return {name for name, value in required.items() if value in (None, "")}
```

مدل زبانی در پاسخ خود «mutation پیشنهادی» تولید می‌کند، نه Draft کامل و نه دستور ثبت. برای نمونه می‌تواند پیشنهاد دهد عنوان عوض شود یا کاربر درباره دسته ابهام دارد. برنامه این پیشنهاد را parse می‌کند، فیلدهای مجاز را جدا می‌سازد و اعتبارسنجی دامنه را اجرا می‌کند.

من اجازه ندادم مدل کلید دلخواه بسازد یا شناسه داخلی را از حافظه خود حدس بزند. شناسه شهر و دسته فقط پس از resolution در سرویس مقصد وارد Draft می‌شوند. این مرز ساده، بخش بزرگی از hallucination عملیاتی را حذف می‌کند.

## Mutation نسخه‌دار و مشکل دو پیام نزدیک به هم

در پیام‌رسان یا رابط وب، کاربر ممکن است دو پیام را سریع بفرستد. پردازش مدل نیز زمان ثابت ندارد؛ احتمال دارد پاسخ پیام دوم زودتر از پیام اول آماده شود. اگر هر پردازش آخرین Draft را بدون کنترل بازنویسی کند، اصلاح جدید با نتیجه قدیمی جایگزین می‌شود.

برای این مسئله هر Draft یک `revision` دارد. پردازش پیام نسخه‌ای را که بر اساس آن شروع شده به mutation متصل می‌کند. هنگام commit، نسخه مورد انتظار با نسخه فعلی مقایسه می‌شود. اگر برابر نباشد، mutation کورکورانه اعمال نمی‌شود؛ پیام با state تازه دوباره ارزیابی یا به مسیر conflict فرستاده می‌شود.

```python
def apply_mutation(
    draft: ListingDraft,
    *,
    expected_revision: int,
    changes: dict[str, object],
) -> ListingDraft:
    if draft.revision != expected_revision:
        raise DraftConflict("draft changed while the message was processed")

    allowed = {"title", "description", "phone", "address"}
    safe_changes = {key: value for key, value in changes.items() if key in allowed}
    return draft.model_copy(
        update={**safe_changes, "revision": draft.revision + 1}
    )
```

در نسخه عملی، ذخیره و تغییر state باید در تراکنش یا عملیات اتمیک storage انجام شود. قفل سراسری راه‌حل خوبی نیست، چون نشست‌های مستقل را بی‌دلیل پشت هم قرار می‌دهد. قفل یا compare-and-swap باید در سطح session باشد.

## Resolution: تفاوت متن کاربر با شناسه معتبر مقصد

کاربر می‌گوید «تعمیر خودرو»، اما مقصد ممکن است دسته‌هایی با عناوین نزدیک داشته باشد. مدل زبانی می‌تواند چند گزینه را پیشنهاد کند، ولی تصمیم نهایی باید روی داده واقعی taxonomy انجام شود. جریان من ابتدا عبارت را نرمال می‌کند، سپس گزینه‌های مقصد را جست‌وجو می‌کند و فقط در صورت تطبیق مطمئن شناسه را قرار می‌دهد.

اگر چند گزینه نزدیک وجود داشته باشد، state به `NEEDS_RESOLUTION` می‌رود و گزینه‌ها به کاربر نمایش داده می‌شوند. انتخاب کاربر همراه شناسه گزینه ثبت می‌شود. این کار کمی اصطکاک ایجاد می‌کند، اما بهتر از ثبت کسب‌وکار در دسته اشتباه است.

برای شهر نیز نام فارسی، شکل‌های نوشتاری و وابستگی استان اهمیت دارد. حذف فاصله، یکسان‌سازی «ي/ی» و «ك/ک» و trim مفید است، اما نباید دو موجودیت واقعاً متفاوت را صرفاً به دلیل شباهت متن یکی دانست.

یک trade-off مهم اینجا سرعت در برابر قطعیت است. اگر سیستم برای هر فیلد پرسش جداگانه بپرسد، مکالمه خسته‌کننده می‌شود. اگر همه چیز را خودکار فرض کند، احتمال خطا بالا می‌رود. راه میانی من این بود که مقادیر قطعی بدون سؤال اضافه شوند و فقط ابهام مؤثر بر ثبت، سؤال ایجاد کند.

## دروازه تأیید و باطل‌شدن تأیید قدیمی

پس از تکمیل فیلدهای ضروری، سیستم یک خلاصه قابل خواندن تولید می‌کند. این خلاصه از Draft ساخته می‌شود، نه از متن آزاد مدل. کاربر دقیقاً می‌بیند چه چیزی قرار است ثبت شود. همراه خلاصه، revision فعلی نیز در state تأیید ذخیره می‌شود.

اگر کاربر بگوید «تأیید»، برنامه ابتدا بررسی می‌کند Draft هنوز همان revision است. اگر پس از نمایش خلاصه هر تغییری انجام شده باشد، تأیید قدیمی معتبر نیست و خلاصه تازه نمایش داده می‌شود. این قاعده جلوی یک race ظریف را می‌گیرد: تأیید اطلاعاتی که دیگر نسخه جاری نیستند.

پذیرش تأیید نیز به match ساده کلمه محدود نشد. «تأیید نمی‌کنم» شامل واژه تأیید است ولی معنای مخالف دارد. intent استخراج‌شده یک ورودی است، اما در مرحله حساس از الگوهای قطعی و دکمه صریح رابط استفاده می‌شود. در صورت ابهام، سیستم اثر جانبی انجام نمی‌دهد.

## Idempotency در مرز ثبت نهایی

حتی اگر state داخلی درست باشد، timeout پس از ارسال درخواست می‌تواند نتیجه را نامشخص کند. شاید مقصد رکورد را ساخته ولی پاسخ به دست ما نرسیده باشد. retry با payload مشابه بدون کلید پایدار، رکورد دوم می‌سازد.

برای هر تلاش منطقی ثبت، یک idempotency key ساخته و تا تعیین نتیجه حفظ می‌شود. کلید با هر retry شبکه عوض نمی‌شود. مقصد باید این کلید را ذخیره و پاسخ همان عملیات را برگرداند. اگر API مقصد این قابلیت را ندارد، یک شناسه خارجی یکتا در payload و lookup پس از خطا می‌تواند جایگزین محدودتری باشد.

```python
async def submit_draft(session: SessionState) -> SubmissionResult:
    if session.state != ConversationState.AWAITING_CONFIRMATION:
        raise InvalidTransition("explicit confirmation is required")
    if session.confirmed_revision != session.draft.revision:
        raise DraftConflict("confirmation belongs to an older revision")

    payload = build_destination_payload(session.draft)
    result = await importer.create_listing(
        payload,
        idempotency_key=session.submission_key,
    )
    if not result.entity_id:
        raise UnknownSubmissionOutcome("destination returned no entity id")
    return result
```

کد واقعی جزئیات بیشتری برای timeout، پاسخ نامعتبر و خطای validation دارد. اصل مهم این است که status code دوصد به‌تنهایی موفقیت نهایی نیست و exception شبکه هم به‌تنهایی شکست قطعی نیست. وضعیت `unknown outcome` باید وجود داشته باشد تا سیستم بدون بررسی، عملیات تازه‌ای نسازد.

## Failure modeهایی که عمداً طراحی شدند

من پیش از تکمیل happy path، چند شکست را به‌عنوان رفتار عادی سیستم نوشتم:

1. **پاسخ مدل JSON معتبر نیست:** پیام اثر جانبی ندارد؛ parse محدود retry می‌شود و سپس درخواست روشن‌تری از کاربر یا fallback نمایش داده می‌شود.
2. **taxonomy مقصد در دسترس نیست:** Draft حفظ می‌شود و سیستم ثبت را عقب می‌اندازد. شناسه حدسی جایگزین نمی‌شود.
3. **کاربر فیلد تأییدشده را اصلاح می‌کند:** revision افزایش می‌یابد و confirmation قبلی باطل می‌شود.
4. **دو worker یک نشست را پردازش می‌کنند:** compare-and-swap یا قفل session اجازه commit هم‌زمان نمی‌دهد.
5. **مقصد timeout می‌دهد:** عملیات در حالت نتیجه نامشخص می‌ماند؛ با همان کلید استعلام یا retry می‌شود.
6. **پاسخ مقصد موفق ولی بدون شناسه است:** `COMPLETED` ثبت نمی‌شود و داده برای بررسی نگه داشته می‌شود.
7. **کاربر لغو می‌کند:** عملیات فعال باطل می‌شود، اما تاریخچه ممیزی حذف نمی‌شود.

نوشتن این سناریوها باعث شد مدل state از ابتدا جا برای وضعیت‌های واقعی داشته باشد. اگر تنها مسیر موفق طراحی شود، خطاها معمولاً به چند `except Exception` و پیام عمومی تبدیل می‌شوند و معلوم نیست سیستم بعد از آن در چه وضعیتی قرار دارد.

## روش تست: مدل زبانی را از منطق قطعی جدا کنید

تست کل سیستم با API واقعی مدل هم کند و هم ناپایدار است. من مرز استخراج پیشنهاد را پشت interface قرار دادم و در بیشتر تست‌ها پاسخ مدل fake می‌شود. این کار اجازه می‌دهد transitionها به‌شکل قطعی بررسی شوند.

تست‌های مهم شامل این موارد هستند:

- Draft ناقص هرگز به `SUBMITTING` نمی‌رسد.
- mutation با revision قدیمی رد می‌شود.
- اصلاح پس از review، confirmation را پاک می‌کند.
- پاسخ منفی شامل کلمه «تأیید» به‌عنوان قبول تفسیر نمی‌شود.
- retry با همان submission key انجام می‌شود.
- پاسخ بدون entity id موفقیت نهایی محسوب نمی‌شود.
- tenant یا session دیگر نمی‌تواند Draft را بخواند یا تغییر دهد.

در کنار تست واحد، چند سناریوی integration با storage و API fake لازم است. برای کیفیت درک فارسی نیز مجموعه کوچکی از مکالمات واقعی ولی ناشناس ساخته می‌شود: اصلاح شماره، نام چندکلمه‌ای، شهر هم‌نام، پیام کوتاه و تغییر نظر. معیار فقط «جواب زیبا» نیست؛ باید دید فیلد درست تغییر کرده، سؤال اضافه بی‌دلیل تولید نشده و هیچ اثر جانبی بدون تأیید رخ نداده است.

## راه‌حل‌هایی که کنار گذاشتم

**دادن کل تاریخچه به مدل و درخواست payload نهایی** ساده بود، اما reproducibility و ممیزی ضعیفی داشت. هر اجرا می‌توانست خروجی متفاوت بدهد و تشخیص منشأ مقدار سخت بود.

**یک prompt بسیار طولانی برای همه قواعد دامنه** نیز کنار گذاشته شد. قواعد قطعی مانند طول تلفن یا وجود دسته در دیتابیس باید در کد باشند. prompt محل مناسبی برای enforce کردن constraint امنیتی نیست.

**ثبت خودکار بعد از کامل‌شدن فیلدها** اصطکاک را کم می‌کرد، اما کاربر فرصت دیدن برداشت اشتباه سیستم را از دست می‌داد. در داده تولیدی، یک مرحله review ارزش زمان کوتاه اضافه را داشت.

**قفل سراسری پردازش** race را کاهش می‌داد ولی ظرفیت سیستم را بی‌دلیل محدود می‌کرد. کنترل نسخه در سطح نشست هم دقیق‌تر و هم مقیاس‌پذیرتر بود.

## محدودیت‌های راه‌حل

State Machine پیچیدگی را حذف نمی‌کند؛ آن را قابل مشاهده می‌سازد. اضافه‌شدن وضعیت زیاد بدون نام‌گذاری روشن نیز می‌تواند نگهداری را سخت کند. migration stateهای ذخیره‌شده هنگام تغییر نسخه جریان مسئله دیگری است و باید از ابتدا نسخه schema یا workflow در نظر گرفته شود.

تأیید صریح نیز تضمین نمی‌کند کاربر همه جزئیات را دقیق خوانده است. طراحی خلاصه، برجسته‌کردن فیلدهای مهم و امکان اصلاح ساده همچنان اهمیت دارد. idempotency هم فقط زمانی کامل است که مقصد آن را پشتیبانی کند؛ پیاده‌سازی یک‌طرفه در کلاینت نمی‌تواند تمام raceهای سمت سرور را حل کند.

مدل زبانی ممکن است در زبان محاوره یا ورودی نامعمول ضعیف عمل کند. برای همین باید نرخ fallback، فیلدهای پرتکرار در خطا و علت بازگشت کاربر اندازه‌گیری شود. بدون مشاهده‌پذیری، تیم فقط نمونه‌های موفق را می‌بیند و کیفیت واقعی جریان پنهان می‌ماند.

## جمع‌بندی عملی

در یک دستیار دارای اثر جانبی، مدل زبانی بهتر است نقش مترجم میان زبان طبیعی و mutation پیشنهادی را داشته باشد. Draft ساخت‌یافته منبع حقیقت است، State Machine انتقال‌های مجاز را مشخص می‌کند، validation قطعی از قرارداد دامنه محافظت می‌کند و confirmation مرز اختیار کاربر را نگه می‌دارد. در نهایت idempotency و وضعیت نتیجه نامشخص از تکرار عملیات در شرایط واقعی شبکه جلوگیری می‌کنند.

این معماری برای هر چت‌بات ساده لازم نیست. اگر سیستم فقط پاسخ اطلاعاتی می‌دهد و داده‌ای را تغییر نمی‌دهد، ممکن است طراحی سبک‌تری کافی باشد. اما هرجا Agent قرار است حساب بسازد، سفارش ثبت کند یا داده تولیدی را تغییر دهد، بهتر است پرسش اصلی این نباشد که «prompt چقدر خوب است؟»؛ باید پرسید «چه کسی اجازه اثر جانبی را صادر می‌کند و نتیجه آن چگونه قابل اثبات است؟»
