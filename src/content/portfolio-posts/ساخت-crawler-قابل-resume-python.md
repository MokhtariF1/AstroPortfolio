اجرای موفق یک scraper روی ده صفحه نشان نمی‌دهد که همان برنامه روی یک کار چندساعته قابل اعتماد است. هرچه مدت اجرا بیشتر شود، احتمال timeout، پاسخ ناقص، تغییر HTML، توقف پردازش یا خاموش‌شدن سیستم به یک نزدیک می‌شود. اگر برنامه فقط یک حلقه داشته باشد که URLها را می‌خواند و در انتها فایل خروجی می‌نویسد، یک شکست می‌تواند ساعت‌ها پیشرفت را مبهم کند.

در Avval Scraper و IranTejarat Scraper با همین مسئله روبه‌رو شدم. داده‌های عمومی از منابع صفحه‌بندی‌شده دریافت می‌شدند و باید بعداً با قواعد مستقل وارد سامانه مقصد می‌شدند. من به crawlerی نیاز داشتم که بتوان آن را عمداً متوقف کرد، دلیل شکست هر واحد کار را نگه داشت و بدون دانلود دوباره همه صفحات ادامه داد. این مقاله معماری همان مسیر را با نمونه‌های پاک‌سازی‌شده توضیح می‌دهد.

## Resume دقیقاً یعنی چه؟

گاهی resume را با ذخیره `last_page=142` پیاده‌سازی می‌کنند. این روش فقط وقتی درست است که صفحات کاملاً ترتیبی، بدون تغییر و مستقل باشند و تمام رکوردهای صفحه قبل با موفقیت ذخیره شده باشند. در عمل ممکن است صفحه 141 دریافت شده ولی parsing نصف رکوردهای آن شکست خورده باشد. ممکن است صفحه 140 بعداً تغییر کند یا صفحه 142 شامل لینک‌هایی باشد که پردازش جزئیات آن‌ها هنوز کامل نشده است.

برای من resume یعنی هر **واحد کار** وضعیت پایدار داشته باشد و برنامه بتواند کارهای ناتمام یا retryable را دوباره پیدا کند. واحد کار بسته به منبع می‌تواند صفحه فهرست، صفحه جزئیات یا یک رکورد استخراج‌شده باشد. checkpoint یک عدد کمکی است، اما منبع حقیقت وضعیت واحدهاست.

حداقل stateهای مفید چنین جریانی عبارت‌اند از:

- `discovered`: URL یا شناسه پیدا شده ولی هنوز دریافت نشده است.
- `fetching`: یک worker آن را برای مدت محدود claim کرده است.
- `fetched`: پاسخ معتبر و snapshot ذخیره شده است.
- `parsed`: داده ساخت‌یافته از snapshot به دست آمده است.
- `retryable`: خطای موقت با زمان تلاش بعدی ثبت شده است.
- `invalid`: پاسخ یا داده خطای قطعی دارد و نیازمند بررسی است.
- `completed`: خروجی مورد انتظار با شناسه پایدار ذخیره شده است.

هر پروژه دقیقاً به همین نام‌ها نیاز ندارد. نکته این است که «امتحان شد» با «تمام شد» یکی نباشد و شکست موقت از داده نامعتبر جدا شود.

## URL تنها شناسه مناسبی برای deduplication نیست

URLها می‌توانند پارامتر رهگیری، اسلش پایانی یا شکل‌های متفاوت برای یک محتوا داشته باشند. پیش از درج کار، URL canonical داخلی ساخته می‌شود: fragment حذف، hostname و scheme نرمال و پارامترهای غیرمؤثر کنار گذاشته می‌شوند. اگر منبع شناسه پایدار رکورد ارائه کند، آن شناسه معمولاً کلید بهتر است.

```python
from urllib.parse import parse_qsl, urlencode, urlsplit, urlunsplit

TRACKING_KEYS = {"utm_source", "utm_medium", "utm_campaign"}

def normalize_url(raw_url: str) -> str:
    parts = urlsplit(raw_url.strip())
    query = [
        (key, value)
        for key, value in parse_qsl(parts.query, keep_blank_values=True)
        if key not in TRACKING_KEYS
    ]
    path = parts.path.rstrip("/") or "/"
    return urlunsplit((parts.scheme.lower(), parts.netloc.lower(), path,
                       urlencode(sorted(query)), ""))
```

پس از نرمال‌سازی، unique constraint دیتابیس آخرین خط دفاع است. بررسی `if not exists` و سپس insert در دو worker race دارد؛ هر دو ممکن است نبود رکورد را ببینند. عملیات `INSERT ... ON CONFLICT` یا معادل ORM باید نتیجه تکراری را به رفتار عادی تبدیل کند.

Deduplication محتوا مرحله دیگری است. دو URL مختلف ممکن است یک آگهی را نشان دهند. در این حالت شناسه منبع، تلفن نرمال‌شده یا hash مجموعه‌ای از فیلدهای پایدار می‌تواند سیگنال باشد. hash نباید از فیلدی ساخته شود که با هر ویرایش کوچک تغییر می‌کند، مگر آنکه هدف تشخیص نسخه محتوا باشد.

## Snapshot: شواهد دریافت را پیش از parsing حفظ کنید

در نسخه‌های ساده، response دریافت و بلافاصله parse می‌شود. اگر parser exception بدهد، شواهدی برای بازتولید خطا باقی نمی‌ماند و باید دوباره به شبکه مراجعه کرد. من پاسخ موفق را به‌عنوان snapshot ذخیره کردم: زمان دریافت، status، content type، hash و بدنه یا مسیر فایل.

این انتخاب چند فایده داشت. تست parser روی fixture واقعی بدون شبکه انجام می‌شد. هنگام تغییر parser می‌توانستم snapshotهای قبلی را دوباره پردازش کنم. اگر منبع موقتاً پاسخ اشتباه می‌داد، آخرین snapshot سالم بدون تصمیم صریح بازنویسی نمی‌شد.

البته نگهداری HTML خام هزینه فضا و ملاحظات حریم خصوصی دارد. سیاست retention لازم است و داده حساس یا غیرضروری نباید برای همیشه ذخیره شود. در این پروژه‌ها فقط داده عمومی موردنیاز پردازش نگهداری می‌شد و snapshot بخشی از backup عمومی سایت نبود.

## تراکنش را دور درخواست شبکه باز نگه ندارید

یک اشتباه رایج این است که worker رکورد را با lock بخواند، درخواست HTTP انجام دهد و سپس وضعیت را update کند؛ همه داخل یک تراکنش. timeout شبکه می‌تواند lock را چندین ثانیه یا دقیقه نگه دارد و workerهای دیگر را متوقف کند.

الگوی من claim کوتاه بود. worker در یک تراکنش کوچک، یک کار آماده را انتخاب و lease زمانی ثبت می‌کند. سپس تراکنش بسته می‌شود و درخواست شبکه انجام می‌گیرد. در پایان، نتیجه با بررسی مالکیت lease ذخیره می‌شود. اگر process از بین برود، پس از انقضای lease کار دوباره قابل claim است.

```python
async def claim_next_job(session, worker_id: str):
    statement = (
        select(CrawlJob)
        .where(CrawlJob.state.in_(["discovered", "retryable"]))
        .where(CrawlJob.next_attempt_at <= utcnow())
        .order_by(CrawlJob.priority.desc(), CrawlJob.id)
        .with_for_update(skip_locked=True)
        .limit(1)
    )
    job = (await session.execute(statement)).scalar_one_or_none()
    if job is None:
        return None

    job.state = "fetching"
    job.claimed_by = worker_id
    job.lease_until = utcnow() + CLAIM_TTL
    await session.commit()
    return job.to_claim()
```

در SQLite امکانات هم‌زمانی محدودتر است و این الگو باید متناسب با آن ساده شود. در PostgreSQL، `SKIP LOCKED` برای تقسیم صف میان workerها مفید است، ولی عدالت کامل صف را تضمین نمی‌کند. ترتیب، اولویت و جلوگیری از starvation باید جدا بررسی شوند.

## Retry فقط برای خطای موقت است

قرار دادن هر exception در حلقه retry، یک صف بی‌پایان از داده خراب می‌سازد. من خطاها را دست‌کم به سه دسته تقسیم کردم:

1. **موقت:** timeout، reset اتصال، پاسخ 429 یا بعضی خطاهای 5xx. این‌ها با backoff و سقف تلاش retry می‌شوند.
2. **قطعی ورودی:** URL نامعتبر، status 404 پایدار یا داده‌ای که قرارداد ضروری را ندارد. این موارد وضعیت invalid یا review می‌گیرند.
3. **خطای برنامه:** exception غیرمنتظره parser یا invariant شکسته. این خطا باید با context ثبت و برای اصلاح کد برجسته شود؛ retry بی‌نهایت آن را درمان نمی‌کند.

Backoff نمایی با jitter از حمله هم‌زمان workerها پس از بازگشت سرویس جلوگیری می‌کند. `Retry-After` منبع در صورت معتبر بودن اولویت دارد. حداکثر تلاش نیز بر اساس هزینه و ماهیت منبع تعیین می‌شود، نه یک عدد جهانی.

```python
import random

def next_delay(attempt: int, *, base: float = 2, cap: float = 300) -> float:
    maximum = min(cap, base * (2 ** max(0, attempt - 1)))
    return random.uniform(maximum / 2, maximum)
```

Jitter باعث می‌شود تست زمان‌بندی غیرقطعی شود؛ در کد واقعی مولد random یا تابع زمان inject می‌شود تا تست مقدار قابل پیش‌بینی داشته باشد.

## نرخ درخواست و احترام به منبع

پایداری فقط درباره سیستم خودمان نیست. crawler نباید فشار غیرضروری به منبع وارد کند. concurrency، فاصله درخواست و سقف retry باید قابل تنظیم باشند. پاسخ 429 یا کاهش نرخ موفقیت علامتی برای پایین‌آوردن سرعت است. شرایط استفاده و محدودیت‌های فنی منبع باید پیش از جمع‌آوری بررسی شوند و تنها داده عمومی موردنیاز پردازش شود.

یک semaphore در process تعداد درخواست هم‌زمان را محدود می‌کند، اما در اجرای چند process کافی نیست. برای ظرفیت مشترک، rate limiter مرکزی یا تقسیم روشن دامنه کار لازم است. همچنین timeout اتصال و timeout خواندن باید جدا باشند؛ timeout بسیار بزرگ worker را بی‌دلیل اشغال می‌کند و timeout خیلی کوتاه خطای مصنوعی می‌سازد.

## توقف امن با signal و نقطه commit روشن

قابلیت توقف دستی برای نگهداری و استقرار لازم است. هنگام دریافت SIGINT یا SIGTERM، برنامه نباید claim تازه بگیرد. کارهای در حال اجرا می‌توانند تا یک مهلت محدود نتیجه خود را ثبت کنند. بعد از آن، lease آن‌ها منقضی می‌شود و اجرای بعدی تصمیم می‌گیرد چه کند.

مشکل اصلی تعریف نقطه commit است. اگر snapshot نوشته شده ولی state هنوز `fetching` است، اجرای بعدی باید بتواند snapshot را پیدا و بدون دانلود دوباره parse کند. عملیات‌ها تا جای ممکن idempotent طراحی می‌شوند: ذخیره snapshot با hash و upsert، درج entity با کلید منبع و update وضعیت با شرط worker/revision.

من یک پیام «خاموش شد» را معادل سلامت نمی‌دانم. shutdown باید شمار کارهای تکمیل‌شده، آزادشده و در حال lease را گزارش کند. اگر timeout shutdown تمام شد، خروجی صریح به اپراتور می‌گوید اجرای بعدی ممکن است leaseهای منقضی را بازیابی کند.

## تغییر HTML و parser دفاعی

HTML منبع قرارداد رسمی و نسخه‌دار نیست. selector می‌تواند با تغییر ظاهر بشکند. parser باید تفاوت میان «فیلد اختیاری وجود ندارد» و «ساختار اصلی قابل تشخیص نیست» را بفهمد. اگر container اصلی صفر بار پیدا شد، تولید رکورد خالی موفقیت نیست.

در IranTejarat Scraper، fixtureهای چند شکل محتوا برای نسخه‌های legacy و جدید مفید بودند. تست parser به جای mock کردن DOM، HTML ذخیره‌شده را می‌خواند و خروجی نرمال را مقایسه می‌کرد. برای تغییرات کوچک، selector جایگزین قابل قبول است؛ اما fallback بیش از حد گسترده ممکن است متن اشتباه را به‌عنوان فیلد درست بپذیرد.

چند invariant ساده کمک می‌کند:

- تعداد آیتم‌های فهرست نباید ناگهان بدون دلیل صفر شود.
- URL جزئیات باید متعلق به دامنه مورد انتظار باشد.
- شناسه منبع پس از normalization نباید خالی باشد.
- فیلدهای عددی پس از parse باید بازه منطقی داشته باشند.
- افت شدید نرخ استخراج باید هشدار ایجاد کند، نه اینکه quietly موفق گزارش شود.

## جداسازی Crawler و Importer

Crawler باید حقیقت منبع را تا حد لازم ثبت کند؛ Importer باید آن را به قرارداد مقصد تبدیل کند. اتصال این دو در یک حلقه، سرعت و failure mode مقصد را وارد جمع‌آوری می‌کند. اگر API مقصد قطع شود، crawler نیز متوقف می‌شود و شاید دیگر نتوان صفحات منبع را در زمان مناسب دریافت کرد.

با جداسازی، داده خام و نرمال‌شده باقی می‌ماند و importer می‌تواند با نسخه تازه mapping دوباره اجرا شود. وضعیت ارسال، idempotency key و پاسخ مقصد در جدول‌های جدا نگهداری می‌شوند. دیتابیس crawler برای importer read-only است تا یک bug در ارسال، تاریخچه منبع را تغییر ندهد.

این جداسازی هزینه دارد: storage بیشتر، schema میانی و نیاز به ابزار status. برای کار بسیار کوچک یک‌باره شاید لازم نباشد. اما وقتی اجرا تکرارشونده، مقصد حساس یا داده نیازمند بازبینی است، این مرز ارزش خود را نشان می‌دهد.

## مشاهده‌پذیری: فقط لاگ خطا کافی نیست

برای پاسخ به «الان crawler کجاست؟» باید شمار stateها، قدیمی‌ترین کار آماده، تعداد retryها و زمان آخرین موفقیت قابل مشاهده باشد. من CLIهای status و doctor را مفید دیدم. doctor تنظیمات، migration دیتابیس، دسترسی مسیر snapshot و اتصال مقصد را پیش از اجرای طولانی بررسی می‌کند.

لاگ ساخت‌یافته شامل job id، source id، attempt و stage است. بدنه کامل صفحه یا token در لاگ قرار نمی‌گیرد. برای خطای parser، hash snapshot و selector شکست‌خورده از چاپ کل HTML امن‌تر و قابل جست‌وجوتر است.

متریک‌های مفید شامل نرخ fetch موفق، نرخ parse، توزیع status code، اندازه صف retry و سن leaseهاست. عدد کل رکورد به‌تنهایی کیفیت را نشان نمی‌دهد؛ crawlerی که سریع رکورد ناقص تولید می‌کند سالم نیست.

## روش تست

تست را در چند سطح تقسیم کردم:

- **Normalization:** شکل‌های مختلف URL و متن باید خروجی پایدار بسازند.
- **Parser fixture:** HTML واقعی پاک‌سازی‌شده بدون شبکه parse می‌شود.
- **State transition:** خطای موقت به retryable و خطای داده به invalid می‌رود.
- **Deduplication:** درج هم‌زمان یک source id تنها یک entity منطقی می‌سازد.
- **Lease recovery:** کار process متوقف‌شده پس از TTL دوباره قابل claim است.
- **Integration HTTP:** server fake پاسخ‌های 429، 500، timeout و محتوای ناقص تولید می‌کند.
- **Shutdown:** پس از signal، claim تازه متوقف و وضعیت کار جاری مشخص می‌شود.

در تست هم‌زمانی فقط اجرای تابع دوبار پشت سر هم کافی نیست. دو connection جدا باید race واقعی روی unique constraint یا claim را ایجاد کنند. برای PostgreSQL، اجرای integration روی همان موتور از SQLite in-memory قابل اعتمادتر است؛ رفتار lock و نوع داده یکسان نیست.

## راه‌حل‌های ردشده و trade-offها

**فایل JSON واحد برای state** در شروع جذاب بود، ولی update اتمیک چند worker، query وضعیت و migration را دشوار می‌کرد. برای ابزار تک‌process کوچک مناسب است، اما دیتابیس برای این پروژه مسیر رشد بهتری داشت.

**ذخیره فقط خروجی parsed** فضا را کم می‌کرد، اما بازتولید bug parser را سخت می‌کرد. snapshot با retention کنترل‌شده انتخاب شد.

**retry نامحدود** ظاهراً داده بیشتری نجات می‌داد، ولی خطای قطعی را پنهان و منبع را تحت فشار قرار می‌داد. سقف تلاش و dead-letter/review شفاف‌تر بود.

**exactly-once** به‌عنوان وعده کنار گذاشته شد. میان شبکه، دیتابیس و مقصد خارجی، تضمین مطلق معمولاً واقع‌بینانه نیست. طراحی بر at-least-once delivery همراه عملیات idempotent و deduplication متمرکز شد.

## محدودیت‌ها

هیچ crawlerی در برابر تغییر کامل منبع خودکار مقاوم نیست. fixture و هشدار فقط زمان تشخیص را کم می‌کنند. ذخیره snapshot نیز نیازمند سیاست حذف و کنترل دسترسی است. `SKIP LOCKED` صف ساده را کارآمد می‌کند، اما جای message broker را در همه مقیاس‌ها نمی‌گیرد.

Resume دقیق به اندازه granularity state هزینه نوشتن دارد. اگر برای هر لینک و مرحله چند رکورد ثبت شود، دیتابیس و نگهداری پیچیده‌تر می‌شوند. granularity باید با هزینه دوباره‌کاری متناسب باشد: دانلود فایل بزرگ ارزش checkpoint ریزتری نسبت به یک درخواست کوچک دارد.

## جمع‌بندی عملی

Crawler قابل Resume از یک حلقه سریع ساخته نمی‌شود؛ از state پایدار، واحد کار مشخص و مرز commit روشن ساخته می‌شود. URL و موجودیت باید کلید deduplication داشته باشند، snapshot پیش از parsing شواهد خطا را حفظ کند و retry فقط خطاهای موقت را با backoff پوشش دهد. claim کوتاه و lease اجازه می‌دهد چند worker بدون قفل شبکه‌ای طولانی کار کنند.

مهم‌تر از همه، crawler و importer دو مسئله متفاوت‌اند. اولی داده منبع را قابل بازیابی می‌کند و دومی اثر جانبی روی مقصد دارد. وقتی این مرز روشن باشد، قطع شبکه، تغییر parser و اجرای دوباره به یک بحران مبهم تبدیل نمی‌شوند؛ هرکدام state و مسیر بازیابی خود را دارند.
