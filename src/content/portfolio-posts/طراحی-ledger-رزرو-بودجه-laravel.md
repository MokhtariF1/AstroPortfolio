نمایش موجودی در رابط کاربری ساده است: یک عدد از رابط برنامه‌نویسی می‌آید و کنار کیف پول قرار می‌گیرد. اما وقتی این عدد از انجام مأموریت، بودجه کمپین و درخواست برداشت تأثیر می‌گیرد، دیگر یک ستون قابل ویرایش در جدول کاربران کافی نیست. سیستم باید بتواند توضیح دهد هر واحد اعتبار از کجا آمده، تحت چه قانونی صادر شده و آیا بودجه متناظر قبلاً مصرف یا رزرو شده است.

در Mecoin با یک اقتصاد مأموریت‌محور روبه‌رو بودم. کاربر مأموریت انجام می‌داد، پاداش دریافت می‌کرد و در صورت داشتن شرایط، درخواست برداشت ثبت می‌کرد. عملیات هم‌زمان و تلاش مجدد می‌توانستند باعث صدور یا رزرو دوباره شوند. این مقاله مسیر طراحی دفتر کل، خزانه، رزرو بودجه و چرخه برداشت در Laravel را توضیح می‌دهد. نمونه‌ها ساده و پاک‌سازی شده‌اند و هیچ داده مالی واقعی یا جزئیات مشتری در آن‌ها نیست.

## چرا ستون موجودی به‌تنهایی کافی نیست؟

فرض کنید کنترلر تکمیل مأموریت مقدار `balance` را افزایش دهد. اگر همان درخواست به دلیل پایان مهلت از سمت client دوباره ارسال شود، موجودی دوبار زیاد می‌شود. می‌توان یک پرچم `rewarded` روی مأموریت گذاشت، اما دو تراکنش هم‌زمان ممکن است هر دو قبل از به‌روزرسانی آن را false ببینند. علاوه بر آن، فقط می‌دانیم موجودی چقدر است؛ دلیل هر تغییر، سیاست و بودجه پشتیبان آن گم شده‌اند.

در سیستم مالی یا شبه‌مالی، پرسش‌های زیر باید پاسخ قابل اثبات داشته باشند:

- این پاداش مربوط به کدام مأموریت و کدام کاربر است؟
- قانون پاداش در آن زمان چه نسخه‌ای داشت؟
- مبلغ از کدام خزانه یا کمپین تأمین شد؟
- آیا بخشی از بودجه رزرو شده ولی هنوز نهایی نشده است؟
- اگر عملیات لغو شد، با ثبت جبرانی برگشت یا history ویرایش شد؟
- آیا تلاش مجدد همان عملیات است یا یک رویداد تجاری تازه؟

دفتر کل برای پاسخ به این پرسش‌هاست. موجودی می‌تواند حافظه نهان یا نمای محاسبه‌شده باشد، اما رویداد ثبت‌شده منشأ تغییر را حفظ می‌کند.

## مدل دامنه: Account، ورودی دفتر کل و تراکنش

نسخه دقیق دفتر کل به نیاز محصول بستگی دارد. برای این پروژه مفاهیم اصلی عبارت بودند از حساب، تراکنش منطقی و ورودی دفتر کلهای تغییر. هر عملیات تجاری یک شناسه یکتا دارد و ورودی دفتر کلها به آن متصل‌اند. مقدار با عدد صحیح در کوچک‌ترین واحد نگهداری می‌شود؛ float برای ارزش مالی مناسب نیست.

یک مدل ساده‌شده Laravel می‌تواند چنین قاعده تغییرناپذیرهایی داشته باشد:

```php
final class LedgerService
{
    public function creditReward(
        Account $account,
        RewardDecision $decision,
        string $operationKey,
    ): LedgerTransaction {
        return DB::transaction(function () use ($account, $decision, $operationKey) {
            $existing = LedgerTransaction::query()
                ->where('operation_key', $operationKey)
                ->first();

            if ($existing) {
                return $existing;
            }

            $lockedAccount = Account::query()
                ->lockForUpdate()
                ->findOrFail($account->id);

            return $this->recordCredit($lockedAccount, $decision, $operationKey);
        });
    }
}
```

این قطعه‌کد همه جزئیات را نشان نمی‌دهد. یکتا index روی `operation_key` ضروری است؛ check داخل تراکنش به‌تنهایی در همه رقابت هم‌زمانها کافی نیست. اگر دو درخواست هم‌زمان نبود رکورد را ببینند، دیتابیس باید درج دوم را رد کند و سرویس نتیجه عملیات موجود را بازیابی کند.

در دفتر کل ثبت دوطرفه کلاسیک، مجموع debit و credit هر تراکنش صفر است. حتی اگر محصول رابط ساده‌ای دارد، نگاه دوطرفه به انتقال ارزش کمک می‌کند منشأ و مقصد روشن بمانند. برای نمونه صدور پاداش می‌تواند انتقال از خزانه کمپین به حساب کاربر باشد، نه ایجاد عدد از هیچ.

## خزانه و تفاوت آزاد، رزروشده و مصرف‌شده

بودجه کمپین یک عدد واحد نیست. بخشی ممکن است آزاد، بخشی برای عملیات در حال انجام رزرو و بخشی نهایی مصرف شده باشد. اگر فقط `remaining_بودجه` کم شود، لغو یا پایان مهلت مسیر مبهمی ایجاد می‌کند.

مدل مفهومی من سه مقدار را از رویدادها یا نمای محاسبه‌شده دنبال می‌کند:

- **آزاد:** ظرفیتی که هنوز می‌توان رزرو کرد.
- **رزروشده:** ظرفیت متصل به عملیات باز که دیگر برای عملیات دیگر آزاد نیست.
- **مصرف‌شده:** مقدار نهایی‌شده که رویداد مالی متناظر دارد.

قانون اصلی این است که `available` هیچ‌گاه منفی نشود و هر رزرو یک owner و عملیات کلید داشته باشد. رزرو در تراکنش با قفل مناسب انجام می‌شود. بررسی موجودی بیرون تراکنش و سپس به‌روزرسانی، رقابت هم‌زمان کلاسیک check-then-act است.

```php
public function reserve(
    CampaignTreasury $treasury,
    int $amount,
    string $operationKey,
): BudgetReservation {
    return DB::transaction(function () use ($treasury, $amount, $operationKey) {
        $treasury = CampaignTreasury::query()
            ->lockForUpdate()
            ->findOrFail($treasury->id);

        $existing = BudgetReservation::query()
            ->where('operation_key', $operationKey)
            ->first();
        if ($existing) {
            return $existing;
        }

        if ($treasury->available_amount < $amount) {
            throw new InsufficientBudget();
        }

        $treasury->decrement('available_amount', $amount);
        $treasury->increment('reserved_amount', $amount);

        return $treasury->reservations()->create([
            'amount' => $amount,
            'operation_key' => $operationKey,
            'state' => 'active',
        ]);
    });
}
```

ترتیب قفلها باید در همه سرویس‌ها یکسان باشد تا احتمال بن‌بست کاهش یابد. اگر عملیات چند خزانه را لمس می‌کند، شناسه‌ها به ترتیب ثابت قفل می‌شوند. بن‌بست ممکن است با وجود طراحی خوب رخ دهد؛ تراکنش باید تلاش مجدد محدود و آگاهانه داشته باشد، بدون آنکه عملیات کلید تازه بسازد.

## چرخه عمر رزرو

رزرو فقط فعال و حذف‌شده نیست. وضعیت‌های مفهومی شامل فعال، ثبت‌نهایی‌شده، آزادشده و منقضی‌شده بودند. ثبت نهایی یعنی اثر تجاری نهایی شده و مبلغ از رزروشده به مصرف‌شده منتقل می‌شود. آزادسازی یعنی عملیات لغو یا رد شده و ظرفیت به آزاد برمی‌گردد. انقضا برای رزروی است که مدت مجاز آن گذشته، اما آزادسازی باید با اطمینان از نبود عملیات در حال ثبت نهایی انجام شود.

ویرایش مستقیم وضعیت بدون سرویس دامنه خطرناک است. هر انتقال وضعیت هم دفتر کل یا تغییر خزانه متناظر دارد و باید اتمیک باشد. برای مثال آزادسازی دوباره نباید بودجه را دوبار آزاد کند. عملیات و یکتا محدودیت تضمین می‌کنند انتقال وضعیت تکراری همان نتیجه قبلی را برگرداند.

من حذف فیزیکی رزرو را انتخاب مناسبی نمی‌دانم، چون تاریخچه تصمیم از بین می‌رود. وضعیت نهایی، زمان و علت آزادسازی برای ممیزی باقی می‌ماند. اگر حجم داده بالا رفت، archive راه بهتری از حذف شواهد مالی است.

## سیاست نسخه‌دار؛ قانون امروز نباید گذشته را بازنویسی کند

مبلغ پاداش ممکن است با نوع مأموریت، کمپین یا زمان تغییر کند. اگر دفتر کل فقط به جدول سیاست جاری join شود، ویرایش سیاست باعث می‌شود نتوان فهمید تصمیم قدیمی با چه قانونی گرفته شده است.

در زمان تصمیم، `policy_version` و داده‌های مؤثر یا نسخه ذخیره‌شده محدود سیاست کنار RewardDecision ذخیره می‌شوند. هدف کپی کل تنظیمات نیست؛ باید حداقل اطلاعات لازم برای بازسازی دلیل مبلغ حفظ شود. سیاست منتشرشده immutable است و تغییر بعدی نسخه تازه می‌سازد.

این طراحی امکان پاسخ به اختلاف را فراهم می‌کند. اگر کاربر بپرسد چرا پاداش قدیمی با امروز فرق دارد، تراکنش به نسخه قانون خودش متصل است. همچنین انتشار مرحله‌ای سیاست جدید قابل کنترل می‌شود و پردازشگر قدیمی ناخواسته قاعده تازه را وسط عملیات اعمال نمی‌کند.

## کلید تکرارامنی از رویداد تجاری می‌آید

ساخت UUID در هر HTTP درخواست تکرارامنی ایجاد نمی‌کند. کلید باید هویت رویداد تجاری باشد؛ برای نمونه `mission-completion:{user_id}:{mission_id}:{cycle}`. ساختار واقعی باید حریم خصوصی و امکان حدس را در نظر بگیرد، اما معنای آن ثابت است: تکمیل یک مأموریت مشخص در یک دوره مشخص.

کلید روی تراکنش و رزرو یکتا است. تلاش مجدد کنترل‌گر، صف کار صف یا وب‌هوک همان کلید را می‌فرستد. اگر عملیات قبلاً تکمیل‌شده است، همان نتیجه بازگردانده می‌شود. اگر processing یا unknown باشد، سرویس آن را عملیات تازه تلقی نمی‌کند.

انتخاب ریزدانه‌بودن کلید مهم است. اگر مأموریت واقعاً چندبار قابل انجام است، حذف دوره پاداش‌های معتبر بعدی را مسدود می‌کند. اگر دوره از timestamp هر درخواست ساخته شود، تلاش مجدد کلید متفاوت می‌گیرد. domain باید دقیقاً تعریف کند «یک بار» یعنی چه.

## مرز تراکنش و ارسال کار صف

گاهی پس از ثبت نهایی مالی باید اعلان یا پیام ارسال شود. اگر کار صف قبل از ثبت نهایی ارسال شود، پردازشگر ممکن است رکوردی را بخواند که هنوز ثبت نهایی نشده یا بعداً بازگردانی می‌شود. Laravel امکان ارسال after ثبت نهایی را دارد و برای این موارد مفید است.

برعکس، قرار دادن تماس HTTP خارجی داخل تراکنش مالی قفل را طولانی می‌کند. الگوی صندوق خروجی راه بهتری است: در همان تراکنش یک رویداد صندوق خروجی ثبت می‌شود و پردازشگر بعداً آن را ارسال می‌کند. صندوق خروجی نیز تکرارامنی و وضعیت تحویل خودش را دارد.

این معماری consistency فوری همه سیستم‌ها را وعده نمی‌دهد. دفتر کل و رزرو داخل دیتابیس اصلی اتمیک‌اند، اما اعلان eventually consistent است. رابط باید این تفاوت را بشناسد و شکست پیام را معادل شکست پاداش نمایش ندهد.

## چرخه برداشت وجه

برداشت حساس‌تر از پاداش نمایشی است و باید گردش‌کار صریح داشته باشد. وضعیت‌های مفهومی شامل requested، under_review، approved، ردشده، processing، paid و failed هستند. انتقال وضعیتها مجوز، پیش‌شرط و کنشگر مشخص دارند.

هنگام درخواست، مقدار قابل برداشت باید در تراکنش بررسی و مبلغ نگه‌داشته‌شده یا رزرو متناظر ساخته شود. اگر فقط موجودی بررسی شود ولی نگه داشته نشود، کاربر می‌تواند چند درخواست هم‌زمان ثبت کند. یکتا قاعده برای درخواست فعال و قفل حساب جلوی مصرف چندباره ظرفیت را می‌گیرند.

تأیید مدیر به‌تنهایی نباید پرداخت خارجی را داخل همان درخواست طولانی اجرا کند. یک عملیات پایدار ساخته می‌شود و پردازشگر با تکرارامنی کلید پرداخت را انجام می‌دهد. پایان مهلت سرویس پرداخت به وضعیت نامشخص می‌رود و پیش از تلاش مجدد نیازمند استعلام است. پس از اثبات پرداخت، دفتر کل نهایی و مبلغ نگه‌داشته‌شده مصرف می‌شود.

رد درخواست مبلغ نگه‌داشته‌شده را آزاد می‌کند، اما تاریخچه درخواست و کنشگر باقی می‌ماند. ویرایش مستقیم وضعیت در دیتابیس مسیر پذیرفته‌شده نیست؛ فرمان دامنه باید قاعده تغییرناپذیر مالی را همراه انتقال وضعیت اجرا کند.

## مجوز و امنیت

کاربر نباید مبلغ پاداش یا حساب خزانه را در داده ارسالی تعیین کند. ورودی فقط شناسه عملیات مجاز را ارائه می‌کند و سرور مبلغ را از سیاست نسخه‌دار محاسبه می‌کند. سیاستهای Laravel مجوز دیدن یا تغییر درخواست برداشت را کنترل می‌کنند، ولی قاعده تغییرناپذیر مالی در سرویس دامنه نیز اعمال می‌شود.

مقادیر مالی به‌صورت integer و currency/asset صریح ذخیره می‌شوند. ترکیب دارایی‌های متفاوت در یک موجودی بدون نوع، خطای دامنه است. mass assignment محدود می‌شود و model event جادویی برای عملیات اصلی مالی انتخاب خوبی نیست؛ جریان باید در service قابل دنبال‌کردن باشد.

لاگ‌ها عملیات کلید و تراکنش id را دارند، اما اطلاعات پرداخت و داده شخصی کامل را نمایش نمی‌دهند. دسترسی مدیر به گردش‌کار ثبت ممیزی می‌شود. محدودسازی نرخ و احراز هویت جلوی تلاش مجدد مخرب را کامل نمی‌گیرند، ولی سطح حمله را کاهش می‌دهند؛ دفاع نهایی همان تکرارامنی و قاعده تغییرناپذیر دیتابیس است.

## روش تست

تست مالی فقط بررسی وضعیت 200 نیست. قاعده تغییرناپذیرها باید مستقیم آزموده شوند:

- اجرای دوباره completion با یک عملیات کلید فقط یک reward می‌سازد.
- دو درخواست موازی بیشتر از آزاد بودجه رزرو نمی‌کنند.
- آزادسازی تکراری آزاد را دوبار افزایش نمی‌دهد.
- ثبت نهایی فقط رزرو فعال را مصرف می‌کند.
- تغییر سیاست جاری، مبلغ تراکنش گذشته را عوض نمی‌کند.
- کاربر نمی‌تواند مبلغ محاسبه‌شده سمت سرور را override کند.
- دو درخواست برداشت هم‌زمان ظرفیت یکسان را مصرف نمی‌کنند.
- شکست اعلان پس از ثبت نهایی، دفتر کل را بازگردانی نمی‌کند.

برای هم‌زمانی، دو connection دیتابیس و barrier لازم است تا هر دو عملیات تقریباً هم‌زمان به نقطه بحرانی برسند. اجرای sequential همان bug را آشکار نمی‌کند. تست Feature Laravel برای نقطه پایانی مفید است، اما تست service با دیتابیس واقعی نیز باید محدودیت و قفل را پوشش دهد.

Property-based thinking حتی بدون ابزار خاص کمک می‌کند. بعد از هر دنباله reserve، آزادسازی و ثبت نهایی باید رابطه خزانه برقرار باشد و هیچ مقدار منفی نشود. مجموع ورودی دفتر کلهای تراکنش دوطرفه باید قاعده تغییرناپذیر خودش را حفظ کند.

تست E2E با Playwright روی مسیر کاربر و مدیر تمرکز دارد: نمایش موجودی، ثبت درخواست، عدم امکان ثبت دوباره و نمایش وضعیت. اما Playwright جای تست رقابت هم‌زمان دیتابیس را نمی‌گیرد؛ هر سطح تست سؤال متفاوتی دارد.

## حالت‌های شکست مهم

1. **درخواست completion تکراری:** یکتا عملیات کلید نتیجه قبلی را برمی‌گرداند.
2. **بن‌بست دیتابیس:** تراکنش محدود با همان کلید تلاش مجدد می‌شود؛ عملیات تازه ساخته نمی‌شود.
3. **کار صف پس از ثبت نهایی دوبار اجرا می‌شود:** پردازش‌گر صندوق خروجی تکرارامن است.
4. **رزرو فعال بدون ادامه می‌ماند:** پاک‌ساز دوره‌ای پس از مهلت و بررسی وضعیت آن را آزاد یا برای بازبینی علامت می‌زند.
5. **پرداخت پایان مهلت می‌دهد:** درخواست به paid یا failed حدسی نمی‌رود؛ تطبیق نتیجه لازم است.
6. **سیاست میان شروع و ثبت نهایی تغییر می‌کند:** RewardDecision به نسخه انتخاب‌شده متصل می‌ماند.
7. **نمای محاسبه‌شده موجودی خراب می‌شود:** دفتر کل امکان محاسبه و تطبیق نتیجه را فراهم می‌کند.

آخرین مورد دلیل دیگری است که دفتر کل را منبع شواهد می‌دانم. نمای محاسبه‌شده برای سرعت مفید است، اما باید بتوان اختلاف آن با ورودی دفتر کلها را تشخیص داد. فرمان دوره‌ای تطبیق نتیجه حساب‌های ناسازگار را گزارش می‌کند و اصلاح خودکار بدون ثبت جبرانی انجام نمی‌شود.

## راه‌حل‌های ردشده

**افزایش مستقیم موجودی در کنترل‌گر** به دلیل نبود ممیزی و رقابت هم‌زمان کنار گذاشته شد.

**یک جدول تراکنش با مقدار signed بدون منشأ و عملیات** برای گزارش ساده بود، اما انتقال میان خزانه و کاربر را خوب توضیح نمی‌داد.

**حذف رکورد هنگام بازگردانی تجاری** تاریخچه را از بین می‌برد. ورودی دفتر کل یا انتقال وضعیت جبرانی انتخاب شد.

**اعتماد به صف برای اجرای دقیقاً یک‌باره** اشتباه بود. صف ممکن است کار صف را دست‌کم یک‌بار تحویل دهد؛ پردازش‌گر باید تکرارامن باشد.

**قفل application-level بدون محدودیت دیتابیس** در چند فرایند قابل اتکا نبود. قفل و یکتا index نزدیک منبع حقیقت قرار گرفتند.

## بده‌بستان و محدودیت‌ها

دفتر کل جدول‌ها و کد بیشتری نسبت به موجودی ساده دارد. query گزارش نیز پیچیده‌تر می‌شود و تیم باید مفهوم عملیات، ورودی دفتر کل و رزرو را درست بفهمد. برای یک امتیاز تزئینی بدون ارزش و بدون برداشت، این هزینه شاید ضروری نباشد. انتخاب باید متناسب با ریسک محصول باشد.

نگهداری موجودی نمای محاسبه‌شده نیازمند تطبیق نتیجه است. محاسبه موجودی فقط از کل دفتر کل در هر درخواست می‌تواند کند باشد، ولی حافظه نهان بدون کنترل هم خطر drift دارد. این پروژه نمای محاسبه‌شده تراکنشی همراه امکان بازسازی را ترجیح داد.

MySQL و PostgreSQL جزئیات قفل و isolation متفاوت دارند. تکیه بر رفتار پیش‌فرض بدون تست روی موتور واقعی اشتباه است. ترتیب قفل، index و طول تراکنش باید با برنامه اجرای پرس‌وجو و بار واقعی بررسی شوند. مقاله حاضر ادعای عدد عملکرد ارائه نمی‌کند، چون آزمون کارایی معتبر محیط تولید برای انتشار ندارم.

## جمع‌بندی عملی

وقتی پاداش به بودجه واقعی و برداشت متصل است، موجودی فقط خروجی سیستم است، نه تمام حقیقت آن. دفتر کل دلیل تغییر، خزانه منشأ ارزش و رزرو ظرفیت در حال مصرف را مشخص می‌کنند. سیاست نسخه‌دار اجازه می‌دهد تصمیم گذشته با قانون امروز بازنویسی نشود و عملیات کلید تکرار درخواست یا کار صف را به اثر مالی دوم تبدیل نکند.

تراکنش کوتاه، قفل با ترتیب ثابت و یکتا محدودیت از رقابت هم‌زمانهای دیتابیس محافظت می‌کنند. تماس خارجی باید بیرون مرز تراکنش و از طریق صندوق خروجی/پردازشگر انجام شود. برای پرداخت نیز پایان مهلت به معنی شکست قطعی نیست و وضعیت نامشخص نیازمند تطبیق نتیجه است.

این طراحی نسخه جهانی کیف پول نیست و برای هر محصول کوچک لازم نمی‌شود. اما اگر سیستم باید به پرسش «این پول چرا و چند بار جابه‌جا شد؟» پاسخ قابل اثبات بدهد، ثبت رویداد و مرز عملیات از یک ستون موجودی قابل اعتمادتر است.
